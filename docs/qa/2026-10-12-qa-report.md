## 4. JIRA-style tickets

### TMQA-006 — Preserve pending predecessor cleanup after directory sync failure

| Field | Value |
| --- | --- |
| Type / priority / severity | Bug / P2 / Major: 복구 완료 상태의 신뢰성 |
| Component / owner | Device recovery / macOS platform maintainer |
| Status | Fixed / source-level verified; native acceptance NOT_RUN |
| Related | TMQA-003; 기존 build 23의 제한된 physical PASS는 유지 |

**Current State**

`DeviceModeRecoveryJournal.confirmNoActiveRecord()`는 lease 검증과 active record 부재
재확인 뒤 directory sync를 수행합니다. `ProofMapper.restorePreviousMode`의 빈 기록
Retry와 `P16KTDeviceMode.attachRecovery`의 exclusive-open 후 빈 기록 Start가 이 helper를
호출합니다. 실패는 기존 오류 경로로 전달되며 새 기록이 나타나면 보존하고 거부합니다.
특정 nonce를 추측하거나 device I/O를 추가하지 않고 durable file absence만 확인합니다.
Inactive predecessor Quit 허용은 유지하며 이를 cleanup 완료 증거로 삼지 않습니다.

**Baseline finding — `65a8e71`, before fix**

`DeviceModeRecoveryJournal.swift:558–564`는 record를 unlink한 뒤 `pendingRemoval`을 저장하고 directory sync를 수행합니다. 새 owner가 predecessor record를 복구하는 경우 `ownedNonce`는 없으며 `hasOwnedActiveRecord`도 false입니다. `P16KTDeviceMode.needsRestore`(`:15–19`)에는 pending predecessor removal이 포함되지 않습니다. `attachRecovery`의 삭제 실패는 transaction 재생성(`:174–176`) 전에 발생합니다.

Startup 복구의 control/journal은 `ProofMapper.swift:412–416,438–446`의 로컬 수명에 묶여 있습니다. 실패 뒤 lease를 닫고 다시 얻으면 pending state가 사라지고, record가 없다는 이유로 Retry의 no-record 경로가 성공합니다. `ProofUI.swift:839–865`는 이 성공에 따라 startup error를 지울 수 있습니다. 처음에는 오류를 표시하지만 재시도에서 남은 sync를 수행하지 않는 것이 결함입니다.

**Reproduction and actual result**

1. 임시 private directory에 synthetic old owner의 `(0,0)` record를 저장합니다.
2. synthetic new owner가 predecessor 부재와 같은 identity를 확인합니다.
3. original readback `(0,0)`을 주입하고 unlink 뒤 directory sync만 실패시킵니다.
4. lease를 닫고 다시 얻어 production no-record 분기를 실행합니다.

`[Verified]` record는 현재 경로에서 보이지 않으며 재획득 후 success branch의 directory sync 호출은 **0회**입니다. 같은 lease를 유지할 때 exact record retry는 가능합니다. [명령과 출력](2026-10-12-fault-evidence.md#journal-check)을 보존했습니다. Native `P16KTDeviceMode`나 AppKit UI를 실행한 재현은 아닙니다.

**Impact**

완료되지 않은 durable cleanup을 성공으로 판정할 수 있습니다. `[Inference]` 이후 전원 중단에서 stale record가 다시 나타날 가능성이 있지만 실제 filesystem replay나 잘못된 feature write는 재현하지 않았습니다.

**Expected State / acceptance criteria**

- 동일 predecessor의 pending cleanup을 sync 성공까지 보존하거나 같은 내구성 계약을 충족하는 명시적 완료 경로를 제공해야 합니다.
- unlink 성공/sync 실패 후 Retry는 exact record의 cleanup을 완료하기 전 성공을 표시하지 않아야 합니다.
- 재시도는 mode write 추가, 두 번째 unlink, 다른 nonce overwrite 또는 불일치 identity/owner의 채택을 하지 않아야 합니다.
- 수정 검사는 기존 `DeviceModeRecoveryJournalTests`의 seam을 사용하고 predecessor/new-owner 수명을 포함해야 합니다. 새 device simulator는 필요하지 않습니다.

**Validation / stopping condition**

기존 journal target의 `predecessorRemovalSyncFailureRequiresConfirmedAbsenceBeforeRetrySucceeds`
검사가 new-owner unlink/sync 실패, lease 재획득, 재실패, sync 성공과 새 기록 거부/보존을
확인했습니다. `bash scripts/test.sh`는 App 컴파일과 38개 tests(Platform 25 + Core 13)를
통과했습니다. 주 agent와 별도 reviewer가 실제 두 호출 경로를 확인했으며 이 범위에서
source-level ticket을 닫습니다. Physical power-loss/native acceptance는 NOT_RUN입니다.
기록 삭제나 추측한 mode write를 workaround로 사용하지 않습니다.

### TMQA-007 — Keep DMG and checksum consistent when finalization fails

| Field | Value |
| --- | --- |
| Type / priority / severity | Bug / P2 / Major: release 후보 파일의 불일치 |
| Component / owner | Packaging / release maintainer |
| Status | Fixed / source-level verified with existing mocked-native fixture |
| Related | `Tests/PackagingTests/test_packaging.py`의 `test_dmg_failure_preserves_existing_artifact`와 새 finalization regression |

**Current State**

Staging에서 DMG의 digest와 sidecar를 완성한 뒤 유효한 이전 쌍을 원래 파일명으로
`dist/previous-builds/touch-me-<VERSION>-<UUID>/`에 함께 보관합니다. 이전 sidecar를 먼저
옮기고 새 DMG를 먼저 반영하므로 작업 중단 시 새 DMG와 이전 sidecar가 섞이지 않습니다.
`OSError`는 완료한 이동을 역순으로 되돌립니다. Rollback도 실패하면 추가 이동을
중단하고 final/staging/archive 경로를 표시합니다. 한 파일만 남았거나 digest/filename이
불일치하는 prior pair는 native commands 전에 보존하고 거부합니다. 별도 rename은
crash, power-loss와 concurrent-run atomicity를 보장하지 않습니다.

**Baseline finding — `65a8e71`, before fix**

`scripts/package-dmg.py:144–154`는 이전 DMG를 archive로 이동하고 새 DMG를 최종 경로에 놓은 뒤 hash를 계산하고 `.dmg.sha256`를 씁니다. 마지막 저장이 실패하면 **새 DMG와 이전 digest가 함께 남습니다.** Archive에는 이전 DMG만 남고 대응 sidecar는 함께 보존되지 않습니다. 기존 test는 `hdiutil` 단계의 실패를 확인하며 이 이후 경계를 다루지 않습니다.

**Reproduction and actual result**

1. 기존 `PackagingTests` fixture에서 첫 DMG/sidecar 쌍을 만듭니다.
2. mock `hdiutil`로 내용이 다른 두 번째 이미지를 생성합니다.
3. 최종 sidecar 쓰기에만 `PermissionError`를 주입합니다.
4. 최종 쌍과 archive를 비교합니다.

`[Verified]` active image 보존은 false, sidecar 보존은 true, 두 파일의 hash 일치는 false입니다. 이전 이미지는 archive에 있으며 대응 sidecar 수는 0입니다. 예상한 예외를 포착한 harness의 exit 0은 결함을 확인했다는 뜻입니다. [명령과 출력](2026-10-12-fault-evidence.md#packaging-check)을 보존했습니다. 실제 `dist`나 native DMG는 변경하지 않았습니다.

**Impact**
